# OW Editor — V2: the full editor

> Describes what was missing for the montage screen to become a real video
> editor, in phases that can be built one at a time. Each phase says in its
> title whether it has been done; what V1 delivered is in [`PLAN.md`](PLAN.md)
> §4.
>
> **Progress:** all phases were done. What was deliberately left out is in §5,
> with the reason for each no.

V1 proved the thesis: the system finds the moments, the user assembles them on
the music and the server delivers the video. What it was not yet is an
**editor** — it was a montage screen with a single operation (putting a stretch
of the match on a time track).

This document starts from the code that exists, not from a generic list of
editor features.

---

## 1. Where V1 got to

| Area | Has | Does not have |
|---|---|---|
| Timeline | one track, blocks with move / stretch / trim, magnet on the beat | multiple tracks, markers *(split, copy and multi-select: done in Phase 1)* |
| History | — | **undo/redo** *(done in Phase 1)* |
| Source | the match recording | other videos, images, text, colour |
| Audio | one music track, original audio when there is no track | per-clip volume, fades, ducking the game under the music |
| Effects | none | speed, zoom, transition, colour, freeze, reverse |
| Monitor | seeks inside the original recording | proxy, frame-by-frame scrubbing, waveform of the game audio |
| Export | 1 format, the recording's resolution | aspect ratio, resolution/bitrate, range, watermark |
| Organisation | one draft per match | named montages, duplicate, presets |
| Keyboard | no shortcuts | space, J/K/L, arrows, Ctrl+Z *(done in Phase 1)* |

### The three structural limits

These are not missing features — they are **V1 decisions that block** the
rest. The first three phases exist to knock down one each.

1. **The state is mutable and has no history.** `_cuts` was a `List` changed in
   place in ~30 `setState` calls in `lib/screens/timeline_screen.dart`. There
   was no way to undo, and every new operation was born without undo.

2. **The model is single-track.** In `packages/owcore/owcore/models.py`, a
   `Timeline` was `cuts: list[TimelineCut]`, and a cut only knows *where* it
   comes from (`start_s`), *how long* it lasts (`duration_s`) and *where* it
   goes (`at_s`). There was nowhere to hang speed, scale, text or a second
   layer.

3. **The render cuts and splices; it does not compose.** `_render_timeline` in
   `services/editor/render.py` cuts each stretch into a file, generates black
   for the gaps and concatenates. Transitions, overlays and text **do not fit**
   that format: they require two pieces to exist at the same time, which only a
   `filter_complex` does.

---

## 2. Decisions made

These were decided before the first line, and the plan below already reflects
them.

| Decision | Consequence |
|---|---|
| **Vertical is not a priority** | export goes at the end (Phase 7). The clip model is born with framing in Phase 3, so 9:16 later is not rework — it just does not lead the queue |
| **The editor accepts outside media** | it gets a **media library** (Phase 4): importing video, image and audio, with probe, proxy and thumbnail for each. Phase 3's source model is born ready for it |
| **The effects of a normal editor** | Phase 5 stops being a list of gameplay tricks and covers the set expected from any editor — transition, transform, colour, speed, audio |
| **Migrate V1's drafts** | Phase 3 also converts the single-track `draft` to the new model. Cheap now (one draft per match), expensive later |

### A decision I made

**Effect preview: approximate in the app, faithful on demand.** Cheap
transforms (scale, position, opacity, constant speed) the app draws itself in
real time. For the rest — transition, colour, speed ramp — the app asks the
server for a **short, low-resolution render of the stretch in focus**, using
Phase 2's proxy. It is slower than real time and it is faithful, which is what
matters when deciding. It reuses the existing pipeline instead of
reimplementing ffmpeg in Dart.

---

## 3. What V2 must not break

V1's legacy that still holds, and that constrains the solutions:

- **one decode of the heavy video.** The preprocessor reads the recording once
  and emits small crops. Anything new that needs pixels goes into that pass,
  not a second one;
- **the server renders, the app edits.** The app never composes video: it
  describes what it wants and ffmpeg does it. That is what makes editing on a
  phone possible;
- **empty space is a black screen**, and a block lands where it was put. It is
  the promise that keeps the ruler trustworthy;
- **analysis is separate from rendering**, and the same analysis serves as many
  montages as wanted;
- **nothing paid, no external API.**

---

## 4. The phases

Each phase can be delivered on its own and leaves the editor better than it
found it. The order is not by apparent value — it is by **dependency**: the
first two are foundations, and postponing either makes the rework grow with
the number of operations the editor has.

### Phase 1 — Editing foundation ✅ **done**

> Knocks down limit ①. Without it, each new operation needs rewriting later.
>
> **Delivered.** `frontend/lib/montage_state.dart` (immutable state + history),
> with 29 tests of its own and 13 screen tests. What was left out is at the end
> of this section.

**Backend:** nothing.

**App:**
- immutable state: `_cuts` leaves the screen and becomes a `MontageState`
  (immutable list + selection + music entry), with each operation returning a
  new state;
- a command history with **undo/redo** (Ctrl+Z / Ctrl+Shift+Z), grouping a
  whole drag into a single step — as the autosave already does;
- **multi-select** (shift-click, rectangle) and batch operations;
- **copy / paste / duplicate** blocks;
- **split** at the cursor (razor) — the most requested missing operation;
- **keyboard shortcuts**: space (play), arrows (move the cursor / nudge the
  block), `[` and `]` (trim to the cursor), Delete, J/K/L.

**Why first:** the history has to wrap *every* operation. Doing that with 6
operations costs a day; with 25, it costs a week and comes out full of holes.

**Verification:** `test/montage_state_test.dart` covers the state and history
(immutability, grouping by gesture, stack ceiling);
`test/timeline_screen_test.dart` covers the keyboard path — undoing a whole
drag, splitting, duplicating, copy/paste and multi-select.

**What was left for later:**
- **rectangle selection**: dragging the ruler's background is the gesture that
  scrolls it, and competing for that gesture needed a separate mode.
  Shift-click and Ctrl+A cover the common case;
- **markers** on the timeline — they are not foundation, and fit better with
  Phase 3's tracks.

### Phase 2 — A monitor you can trust ✅ **done**

> V1's weakest link, and the one that already broke in real use.
>
> **Delivered.** The proxy comes out of the decode that already happens, the
> match's waveform is drawn inside each block, and the one-frame step uses the
> recording's real fps.

**Backend:**
- **proxy**: the preprocessor gets a fifth output in the decode that already
  happens — the whole screen reduced (~640px, ~24 fps, high CRF). `RoiSpec`
  already had `fullscreen`, and no profile used it. Cost close to zero, because
  the decode is already paid for;
- a route to serve it, and the monitor opens the proxy instead of the
  recording's 535 MB. The final cut still comes from the original, at full
  quality;
- **the match audio's waveform**, in the same reduced format `beats` already
  produces for the music — it is what shows the shot and the explosion.

**App:**
- a monitor on the proxy: instant seeking, without the player dying;
- **frame-by-frame** scrubbing (arrows with the video paused);
- the game's waveform drawn on the block's track, to match the game sound with
  the music;
- an **editable beat grid**: fixing the BPM and phase when the detector gets it
  wrong, and marking the bar (4/4) so the magnet snaps to the downbeat, not to
  any beat.

**Why here:** editing without seeing properly is guessing. And the proxy is a
prerequisite of the on-demand faithful preview (§2) and of everything imported
media will need.

**Verification:** `test_timeline.py` checks that the proxy covers the whole
match (duration and aspect equal to the original's), that it is smaller, that
it is served with `Range`, and that a match analysed before it answers
`proxy_url: null` — the app falls back to the original recording in that case.

**How it ended up, and what changed from the plan:**
- the proxy went in as one more output of `extract_rois`, with
  `RoiSpec(fullscreen: true, 640px, 24fps)`. It inherits the BT.601 colour tags
  the detectors require — the monitor may look a hair different from the final
  render, which comes from the original file;
- WAV reading and the waveform moved from the rhythm service to
  `owcore/audio.py`: there are now **two** drawn tracks (the music and the
  match), and the computation is one;
- the match's waveform is stored whole in the job, and **each block cuts out the
  piece** it shows. Trimming or stretching changes the drawing by itself,
  without recomputing;
- the **one-frame step** went to `,` and `.`, not the arrows: those keep the
  one-second step, which is the one for navigating. The step comes from the
  recording's `fps`, which the preprocessor now stores;
- the **grid corrections** (offset, ½/1×/2× density, snapping to the bar) live
  in the draft, so they survive an F5, and can be undone like any edit — a
  wrong grid makes every cut snap to the wrong place.

**What was left for later:** matches analysed before this phase have no proxy
or waveform. Regenerating them needs reprocessing the recording, which Phase 3
does when touching the pipeline anyway.

### Phase 3 — A real timeline (multi-track) ✅ **done**

> Knocks down limits ② and ③. It is the big phase, and all the following ones
> depend on it.
>
> **Delivered** on both sides: the layered model, reading the V1 format, the
> filter graph (`owcore/compose.py`), the editor choosing between the two
> render paths, and the interface with stacked layers.

**Model** (`packages/owcore/owcore/models.py`):

```
Timeline
└── tracks: list[Track]          # order = layers, bottom to top
    └── clips: list[Clip]
        ├── source                # recording | media | text | color
        ├── at_s, duration_s      # where it goes in the video
        ├── start_s               # where it starts in the source (video and audio)
        ├── transform             # scale, position, crop, opacity
        ├── speed                 # constant or ramp
        ├── audio                 # volume, fades, mute
        └── transition_in/out     # kind and duration
```

`TimelineCut` becomes the particular case of a `Clip` with `source: recording`
on track 0. The `source` field is born discriminated so Phase 4 could come in
without touching the model — in this phase only `recording` and `color` were
accepted.

**Migration:** each match's `draft` and old renders' `timelines` are converted
to the new format on read, with a test that starts from a real V1 draft and
checks the resulting video is identical. There is one draft per match today;
migrating later would cost much more.

**Render:** `owcore/compose.py` writes the `filter_complex` and **does not run
ffmpeg** — it is pure text assembly, testable without encoding a single frame.
A background canvas covers the whole video and each clip is overlaid onto it
at the right moment. The gap between clips stopped being a special case: it is
where nobody covered the background.

The risk mitigation lives in `Timeline.single_layer`: a single-layer montage,
with no transform or adjusted sound, still goes through V1's cut-and-splice —
where a bad cut costs only itself. The graph comes in when it is needed, and
then an error in it brings the whole render down. That is why the graph path
**does not produce the cuts zip**: the pieces never exist as files, and
cutting them out just for the zip would pay for the montage twice.

Audio, in this phase: with a track, it is the audio, as in V1; without one, the
mix of the clips' own sound applies, respecting volume, fades and mute. Mixing
music *and* game (ducking) is Phase 5's.

**In the app:** stacked layers, with each one's header **outside the scroll** —
it is the reference and must stay visible when the ruler moves. Collision is
now per layer, which is exactly what layers are for. Dragging a clip up or down
takes it to another layer keeping its instant, and refuses if the place is
taken there.

The monitor does not compose, it shows a frame: where two layers overlap it
shows the upper one, which is what the server draws last.

**Verification:** 7 tests on the server and 16 in the app — reading the V1
format, choosing between the two render paths, the two-layer mp4 checked with
`ffprobe`, the trimmed clip that does not move its neighbours, a source that
cannot be rendered yet being refused instead of ignored, and the muted layer.

### Phase 4 — Media library ✅ **done**

> The editor stops being hostage to the match recording.

**Backend.** The generalisation happened, and **without a new table**: `Track`
became `Media` with a `kind` column. The `tracks` columns were already almost
those of a media item — kind, dimensions and the thumbnail and proxy keys were
missing — and schema reconciliation added them with a backfill: the existing
music became items of kind `audio` by themselves.

> The table is still called `tracks`, for historical reasons. Renaming it would
> require migrating data for an aesthetic gain; the model, which is what is
> read in the code, says what it holds.

What each kind gets from the analysis: **audio** → duration, BPM, beats and
waveform; **video** → dimensions, fps, thumbnail and proxy; **image** →
dimensions and thumbnail. The worker is the same loop that already listened to
the music, renamed `MediaAnalyzer` — one more service in the compose would cost
a whole image for thirty lines of work.

The `/api/tracks/...` routes still exist as shells over the library, because
the app uses them and because "the job's music" is a useful name.

**Render.** A media clip is one more input in the graph, and from there on it
goes through the same transforms as a stretch of the recording — that is the
point of having a single clip format. An image goes in on a loop (`-loop 1`)
and lasts whatever the clip asks: how long it stays on screen is the montage's
choice, not a property of the file.

**App:** the sidebar got tabs — Moments and Library — because both answer the
same question: "what do I put in now?". The difference is that the system found
the moments and the user brought the library. Removing from the library an item
that is in the montage is refused: the clip would be orphaned and the request
would be rejected on the server.

**Verification:** 7 tests on the server (one per kind, from upload to the mp4
with the item in the composition) and 5 in the app.

### Phase 5 — Effects ✅ **done**

> The set expected from any editor, and not just what serves gameplay.
>
> Speed, fades, colour, audio mix, zoom with keyframes, freeze and reverse. The
> speed ramp was left out — see the end of the section.

**Done in this half:**

- **constant speed** (0.25× to 4× on screen; 0.1× to 10× in the model). It
  changes how much of the *source* the clip consumes, not how much it takes in
  the video — `duration_s` is still what is dragged on the ruler. The audio
  follows through an `atempo` chain, because the filter only accepts 0.5 and up
  and slow motion below that would come out with the sound intact: being out of
  step is worse than having no sound;
- **fades** to and from the background, per clip;
- **colour**: brightness, contrast and saturation — the three that fix almost
  everything in a gameplay recording;
- **mix**: with the game at zero the music replaces the audio, as in V1; above
  that the two mix, which is what lets the shot come through under it.

**The filter order is the decision that carries the rest.** Speed comes before
everything, because it changes the clip's clock: a half-second fade must last
half a second in the final video, not half a second of the source. And placing
it in time (`setpts=PTS+at/TB`) comes last, when the clip already has the
duration it will take.

A name clash inside the model showed up here: `color` was already a background
clip's solid colour. The content's colour became `fill`; `color` kept the
colour adjustment, which is read more often.

**Done in the second half:**

- **zoom with keyframes**. The points are **fractions of the clip**, not
  seconds, so the animation survives stretching or trimming the block: a zoom
  that closes at the end still closes at the end. In the app it becomes three
  buttons (light, medium, strong), because two movements solve the most used
  effect in a montage and nobody would open a curve editor. (It was first
  built on `crop` with expressions in `t`, which never animated: `crop`
  evaluates its width and height once. It is now `zoompan`, evaluated on every
  frame.)
- **freeze** and **reverse**;
- and a **bug from the first half**: ffmpeg's `fade` paints black, which on an
  upper layer is a dark smear over what should show. With `alpha=1` it reveals.
  Over the black background both come out the same — which is why it went
  unnoticed. There is a test that renders two layers and compares the frame at
  the end of the fade with the lower layer's, frame by frame.

**Crossfade between two clips** did not go in as a field at first: with fades
on the alpha, it **can already be done** by putting the two on different layers
with an overlap — which is exactly what layers are for. Within a layer overlap
is forbidden by invariant, and still is. (Transitions between adjacent clips on
the same layer came later, as a property of the incoming clip.)

**Speed ramp** was left out. It is not a keyframe like the others: speeding up
over time requires the PTS to be the integral of the speed, not its value. The
viable path is slicing the clip into stretches of constant speed — which is
more a model decision than a graph one, and fits better with another phase.

**Verification:** 16 tests — the computation of what speed consumes, the
`atempo` chain, the filter order, keyframe interpolation, the mix, absurd values
refused, and three real renders checked on the pixels: the fade that reveals
the lower layer, the zoom that really zooms in (on a frozen clip, to isolate
the lens from the content) and freeze/reverse.

### Phase 6 — Text and graphics ✅ **done**

> Here lies this editor's edge: **the events are already known**.

**On the server,** a text clip is a **transparent canvas** the size of the
frame with `drawtext` on top. From then on it is a clip like any other: it
moves, fades, travels through layers, gets zoom. Transparent and not black —
otherwise the text would come inside a box.

Size and outline are **fractions of the height**, not pixels: the same montage
comes out the same in 720p and in 4K. And the outline is on by default,
because white text disappears in a bright scene.

Text escaping lives in `owcore/textfx.py`, apart from the graph. It is the kind
of code where one backslash too many slips through review and only shows up
when someone writes `50%` in a label — isolated, it has its own test. The font
is resolved by `owcore/fonts.py`, which **fails loudly** when it finds none:
finding that out in the middle of a render would be worse.

**The edge is in the app.** `lib/labels.dart` writes text from what happened
in the match:

- a **kill counter** that goes up by itself — one label per kill cut, each
  number lasting until the next, so what is on screen is always the current
  one;
- **streak labels** with the game's names (`TRIPLE KILL`, `QUAD KILL`), not a
  count: "3 KILLS" where "TRIPLE KILL" fits sounds like a spreadsheet. The
  window looks at the cuts that are **in the montage**, not the match's events
  — what counts is what the viewer will see in a row.

Everything comes out as an ordinary text clip. The generator is a shortcut, not
a new entity: once created, the labels move and edit like any block.

**Shapes and masks** did not go in — no need for them showed up in a gameplay
montage, and a feature nobody uses is dead weight in the editor.

**Verification:** 9 tests on the server (escaping, size as a fraction, the
transparent canvas, and a render checked on the pixels: the text shows up and
goes away **without leaving a black box**) and 15 in the app, on the
generators.

### Phase 7 — Export ✅ **done**

> The montage does not change: **the window you look at it through does.**

That is why `ExportSpec` lives outside the layers. The same work becomes a
16:9 for YouTube and a 9:16 for Shorts without a clip moving, and going back
costs no undo — what was undone was an output choice, not an edit.

What it holds: **size** (`0` = the recording's), **fps**, **quality** (CRF),
**framing**, **range** and **watermark**.

**Framing** has two legitimate answers, and both stayed: `cover` fills and
crops the excess — in a gameplay montage the action is in the middle, and black
bars on a phone are wasted screen; `contain` shows the whole frame and leaves
bars, for whoever needs what is in the corners (the HUD, the scoreboard). The
choice only shows up on screen when the requested aspect differs from the
recorded one: until then there is nothing to decide.

**Exporting a range is not cutting the finished video.** The clips are
repositioned as if the window were the beginning, and a clip that comes in
halfway has its entry point **in the recording** shifted along, in proportion
to the speed — otherwise the picture would jump. In the app, the shortcut is
"selection only": instead of exporting five minutes to check a two-second
splice, it exports the two seconds, and the montage stays intact.

The **watermark** comes after all the layers, on purpose: a mark some layer
covers is not a watermark. It comes from the same library as Phase 5's, and an
id that is not there is refused at the `POST` — better for the whole render to
fail at the entrance than further along.

**Reuse.** At the time, a fingerprint of what is **seen** — ignoring the audio
on purpose — let a music change become a pass of `add_music` over the video
already assembled, instead of cutting everything again. (It went away in Phase
10, together with the continuous track it assumed.)

**Two things only live verification caught:**

`ExportSpec` reached the compositor and was **ignored in the real pipeline** —
a single-layer montage with no effect went through V1's cut-and-splice path,
which cannot change the aspect ratio or draw a watermark. A 9:16 request came
out 16:9 without complaining, and the tests did not see it because they called
the compositor directly. Now a non-default output alone already takes the
montage off that path.

And the `Job` did not know its own recording's size: without it the editor has
no way of saying whether a 9:16 crops the frame. The new column went in, but
the schema reconciler cannot know what it should hold for an old match — only
the file knows. So the job detail **measures the recording once**, via
`ffprobe` on a temporary S3 address: the header comes via `Range`, and
measuring two gigabytes costs the header, not the two gigabytes.

The draft also started carrying **mix and output format**. They had been left
out since Phase 5 and vanished on an F5 — whoever lowered the game volume and
picked 9:16 does not want to redo both.

**Verification:** 15 tests on the server (`ffprobe` checking each preset's
size, fps and duration; `cover` and `contain` compared on the pixels; the
window repositioning; the mark checked as the last thing drawn; reuse proven
end to end, with and without game sound) and 27 in the app (the presets, the
cut by selection, the size estimate and the panel). And four renders on the
real stack, over the user's 1080p60 recording: `1080x1920` cover and contain,
`854x480@24` of a range of exactly 2.00 s, and the untouched default at
`1920x1080@60`.

### Phase 8 — Organisation and reuse ✅ **done**

> A match yields more than one video, and a way of assembling works for more
> than one match.

**Several named montages.** Until now there was a single one, in a column of
the job itself, and that forced a choice: either the 30 s cut for Shorts or the
long montage. They are different jobs over the same material, and now each has
its own name, with duplicate to experiment without risking the one that is
already good.

The migration is the usual one — **the code that reads is what knows how to
convert the old format**. On the first read, the single draft becomes the first
named montage (from the title it already had) and the column is emptied, so
there are not two truths about the same montage. `PUT /api/jobs/{id}/draft`
still exists and writes to the most recent montage: an app older than the phase
loses the picker, not the work.

**Version history.** It is not undo — that lives in the app and dies with the
tab. They are rare and deliberate markers: a snapshot with every rendered video
(*what came out was this*) and one when the user asks. Keeping a snapshot on
every autosave would fill the database with identical states and make the list
useless for its length, so a snapshot identical to the last is refused with
409, and each montage keeps at most 20.

Restoring never deletes work: the current state becomes a snapshot (`before
restoring`) before the old one comes back to the front. And the copy does not
take the original's history — the snapshots say where *that* montage has been,
and the copy has not been anywhere yet.

**Presets.** A preset does not store cuts — it stores the **way** of cutting.
"Two seconds per kill, fitted to the beat, with zoom and a counter" works for
any match; a list of cuts only works for that one. That is what makes the
second match cost one click.

The `Recipe` says what goes in (which events, with how much run-up before each),
at what size (seconds, or **beats** — and the second reading survives a song
with a different tempo, the first does not), with which effects and texts, and
with which mix and output format. Applying it produces an ordinary montage:
once applied, each block moves and trims like any other. The recipe is a
starting point, not a mould you cannot leave.

The reverse path also exists: **save as preset** reads the montage on screen
instead of asking to describe again what was already done. Size and run-up
come from the cuts' **median**, not the mean — a single block stretched to the
end of the music would pull the mean far from what all the others are. And the
app tries to read the size in beats: if the cuts take a round number of them,
that is what gets stored.

**One thing only live verification caught:** the new routes ended up **after**
the Flutter app's `mount`, which matches any path — and every route registered
after it becomes unreachable. A `POST` to one of them returned 405, because the
file server was what answered. The mount now comes last, with a comment saying
why.

**Verification:** 28 tests on the server (the several montages, migrating the
old draft and the older app still saving, the history with pruning and
non-destructive restore, the refused recipes) and 32 in the app (the recipe
applier, the fit to the beat, reading the recipe from the montage and the
screen's picker). And the whole path checked on the stack, over the real match:
the user's 9-cut draft migrated to "My montage" without losing anything.

### Phase 9 — Music on the ruler ✅ **done**

> Two questions from the user: can the music be cut and moved? can there be
> more than one? Until now the answer to both was no.

The music was a **continuous track** under everything: you pick one, say from
which point of it the video starts, and it plays to the end. It serves the
common case and nothing beyond it — switching tracks midway, leaving a stretch
silent so the play's noise comes through, or putting a chorus only on the
turnaround.

Now the timeline has **audio layers**. An `audio` layer does not enter the
visual stacking: it draws nothing, it only plays. Its blocks are ordinary
clips, with `media_id` pointing at a music track in the library — and because
they are ordinary clips, they already know everything a block knows: cut, move,
trim, duplicate, fit to the beat. There was no need to invent a new object for
the music; it needed to be allowed to be a block.

**The two forms coexisted, and one became the other.** The continuous track
was still the one-click path, and "Cut on the ruler" converted it into a block
that starts where it came in and covers the whole video: the same sound as
before, now with ends to grab.

**The beat grid became per block.** A video with two tracks has two tempos,
and the magnet snapping to the other one's beat would be worse than not
snapping at all: the grid is now that of the music playing under the playhead,
brought into video time by discounting the piece of the track that was left
out.

**What this costs.** Music blocks only exist in the filter graph, so a montage
with them loses V1's cut-and-splice path — it makes decisions about sound that
the graph cannot delegate. `single_layer` refuses the montage because of that,
and `has_music` is what it checks.

The server **refuses** content on the wrong kind of layer: music on a video
layer would make ffmpeg try to resize an audio stream and die with a message
that explains nothing; an image on an audio layer would be worse, because it
would come out silent, with no error, and the problem would be looked for in
the mix.

**One thing only live verification caught:** the selected block's panel called
the music "Event at 00:00" and offered it zoom, freeze and colour — controls
that have nothing to act on in a block that draws nothing. Now it says the
track's name, from which point of it the piece came, and the effects go away.

**Verification:** 14 tests on the server (audio layers in the graph, the mix
with and without game audio, the gap between two blocks, refusals for the
wrong layer, reuse turned off) and 21 in the app (the state operations,
converting the continuous track, the block panel and the magnet following the
music that is playing). And the whole path on the stack, over the real match: a
12s video with two music blocks and a second of silence in the middle — the
silence measures 9 dB below the rest, and correlating each block with the
original mp3 finds the exact point of the music it came from.

A defect from outside the phase showed up along the way: the **preprocessor
was in a restart loop** since the match-waveform phase, because `owcore.audio`
started importing `numpy` and its `requirements.txt` did not ask for it. No new
recording would have been analysed. It is fixed.

### Phase 10 — Music is media ✅ **done**

> "There are two ways of adding audio and they work differently. Keep only the
> one I can manipulate."

Phase 9 left both ways coexisting — the one-click continuous track and the
block on the ruler — and coexisting was the problem: two paths to the same
thing, with different rules, and no hint of which one you were using. **What
can be cut is what was kept.**

**The continuous track left the model, not the files.** `track_id` and
`music_start_s` are still valid input and become, on read, a music block that
starts where the track came in and covers the whole video — the same rule "Cut
on the ruler" applied, now running by itself. It is the usual migration: **the
code that reads converts the old format**, on both sides. A request from an
app older than this phase comes out the other side as a video with music, and
the converted montage never rewrites the old fields — sending them back would
create a second music track under the one that already became a block.

**The library is the only door.** There were two file uploaders: a music-only
panel and the media library. They had been the same table in the database
since Phase 4 — `Track` is audio `Media` — and two places to bring the same
thing was what made it look like there were two kinds of sound. Now music
shows up in the library next to video and images, with its tempo on the label,
and goes onto the ruler like any other item.

**Drag and drop.** Clicking puts it at the playhead — it serves whoever
assembles in order. Dragging puts it where the finger let go, on the track
where it let go, with a rectangle showing the size and place before dropping.
It works for the match's moments and for the library. Dropping music on an
image track is not an error: it means "at this instant", and it goes to the
audio layer; dropping a moment on an audio layer is — a layer either draws or
plays.

**The clock became the video.** While the track was continuous, its player
could rule the time: there was a sound playing from the first frame to the
last. With blocks that come and go there is no player playing the whole video,
so the playhead got a clock of its own and the music started following it — the
block under it plays, at its point that corresponds to that instant, and in
stretches without music the clock runs alone. While a block plays, **it** is
the clock: pulling the sound back on every drift would make an audible hiccup
every few seconds.

**What this cost, said plainly:** Phase 7's reuse of the picture — the same
montage re-exported with another track did not cut everything again — went
away with the continuous track. It assumed a sound that comes afterwards,
outside the graph; with blocks, the sound is assembled together with the
picture. The visual fingerprint and the picture cache left the code together
with the promise they served.

**A defect the change revealed:** the magnet compared the distance of the
block's two edges — start and end — without checking whether they had snapped
to anything. An edge that does not snap stays exactly where the finger let go,
distance zero, and always won. That never showed up because every block was
born with a duration that was a multiple of the bar, and both edges snapped
together; the first block created **before** there was music on the ruler is
born with the default duration, and then the magnet simply did not work.

**Verification:** 234 tests on the server and 267 in the app (dragging from the
shelf and the library to the ruler, the refusal for the wrong layer, the clock
running with no music at all, converting the continuous track on both sides).
And on the stack, over the real match: a request in the **old format** became a
video with music, and correlation says 0.5 s of video matches 5.5 s of the
music — exactly where the continuous track came in. In the app, dragging from
the library to the ruler, playing, and an F5 confirming the block stayed.

### After Phase 10 — what use found ✅ **fixed**

> "The text feature does not show up in the video, and it cannot be positioned.
> Layers cannot be reordered by dragging, and elements cannot be moved between
> them."

Three complaints, and the first hid **three defects stacked on the same path**
— all at warning level, none at error level:

1. **The text canvas came out opaque.** `format=rgba` was requested in the
   video chain, after the source. Too late: `color` had already negotiated
   yuv420p with `drawtext`, drawn opaque black, and the alpha added there is
   born at 1. The text showed up — and the video vanished under it.
   `format=rgba` moved **inside** the source, where transparency still exists.
2. **The position was applied twice.** The text canvas is the size of the frame
   and `drawtext` already puts the line in place inside it; the overlay added
   the same offset again. With `y=-0.5` the line went out the top edge and
   disappeared. Now the text canvas is overlaid at (0,0), and only `drawtext`
   positions it.
3. **`%` brought the whole line down.** Escaped as `\%`, `drawtext` warns
   "Stray %" and **draws nothing** — no error, no broken render, just a video
   without text. The answer is `expansion=none`: without `%{...}` expansion,
   `%` is a character like any other, and needs no escaping.

The first passed the suite because the pixel test compared the frame with text
and the frame without and required them to be **different** — and a black
canvas over everything is also different. The test now looks at both halves:
where the text is, it changes; where it is not, it must stay **identical** to
the video without text.

**Text is now positioned on the monitor.** It was drawn on the ruler and in the
final video, and nowhere in between: to know where the line would land, you had
to render the video. The monitor started drawing it with the same computation
as the server — size as a fraction of the height, position in half-frames — and
dragging it there is how its place is chosen.

**Layers reorder, and the stack was turned the right way up.** Dragging one
header over another swaps the drawing order; there is a handle for the pointer
(immediate drag) and a long press for the finger. And then an inversion showed
up that did not bother anyone while nobody reordered anything: the list of
layers goes from bottom to top — the order the server draws in — and the ruler
showed the first of them on the **top** track. Dragging a layer to the top sent
it behind all the others. Today the top track is the top layer, as in any
editor, and dragging a block up raises it in the stack.

**The shortcuts silenced the text fields.** They are single-key — "S" splits,
Delete removes the selected block — and fired even with the cursor in a field:
typing the video's name split a cut on every "s", and deleting ate a block from
the ruler instead of a letter.

The first fix silenced the **action** and kept the shortcut registered, and
that was not enough: `CallbackShortcuts` marks the key as handled as soon as
some shortcut accepts it, whatever it does, and in the browser a handled key
becomes `preventDefault`. The "s" stopped splitting the cut and still was not
typed — the worst of both worlds. What solves it is **not registering any
shortcut** while someone is typing.

Two pieces complete the fix, and both took a detour: finding out who has focus
via `findAncestorStateOfType<EditableTextState>()` (looking for the
`EditableText` widget passed the tests and failed in the browser's release
build, where types are minified), and giving focus back to the montage in the
fields' `onTapOutside` — nothing takes focus away from a `TextField` on its
own, so one tap on the field left "S" and Delete dead for the rest of the
session.

**Moving a block to another layer now explains the refusal.** The gesture
existed since Phase 3 and refused silently when the target was of another kind,
locked or already had something at that instant — and refusing silently is the
worst of both worlds: the block goes back to its place and whoever dragged does
not know whether the gesture did not take or the operation was not possible.

### Aligning the play to the playhead ✅ **done**

> "Make it possible to align the important moment of a stretch (kill, sleep,
> rock) with the timeline's vertical line."

A block is a **stretch**; the play is an **instant inside it**. The cut starts
before it on purpose — at 70% of the block, to leave run-up — and that is why
aligning by the edge leaves the impact half a second after the beat. The play's
mark was already drawn inside the block since Phase 1; what was missing was
being able to take it to a point.

**The command** puts the play exactly where the playhead is — via the button on
the block's panel or the **M** key, and with no selection it applies to the
block under the cursor (tapping the ruler to position the cursor clears the
selection; asking to choose the block again would be the same gesture twice).

**Two ways to get there, and the difference matters.** Moving the block changes
*when* the scene appears and keeps the run-up; sliding the stretch inside the
block keeps the position on the ruler and swaps *which* piece of the recording
shows there. The command tries the first and falls back to the second when the
neighbours do not let the block through — which is the common case, because a
beat montage has adjacent blocks — and the screen **says which of the two it
did**. It was live verification, over the user's real montage, that showed the
first alone almost never works: it refused with "did not fit" across the whole
ruler.

**The magnet got the play as a target.** Dragging a block with the magnet on,
the candidates to snap become three — the two edges and the play — and
whichever is closest to a beat wins. That is what a beat montage means: the
impact lands on time, and the cut's edge lands wherever it has to.

**The mark lights up** when the play is under the playhead. Without that
confirmation, aligning is an act of faith.

## 5. What V2 deliberately does not do

Saying no is planning too:

- **collaborative** and multi-user editing — the product is for one person at a
  time;
- **chroma key, tracking, advanced colour grading** — they do not serve
  gameplay;
- **multicam** — there is one recording;
- **rendering in the browser** — the server renders, and that is what lets the
  app run on a phone;
- **a timeline in frames instead of seconds** — seconds with decimal places
  already give plenty of precision for beat montages, and frames would tie the
  editor to the recording's fps.

## 6. Build order

```
Phase 1 (foundation) ─┐
                      ├─→  Phase 3 (multi-track + migration)
Phase 2 (monitor)    ─┘              ↓
                           Phase 4 (media library)
                                     ↓
                           Phase 5 (effects)
                                     ↓
                      ┌──────────────┴──────────────┐
                      ↓                             ↓
            Phase 6 (text)                Phase 7 (export)
                      └──────────────┬──────────────┘
                                     ↓
                           Phase 8 (organisation)
                                     ↓
                           Phase 9 (music on the ruler)
                                     ↓
                           Phase 10 (music is media)
```

Phases 1 and 2 are independent of each other and can come out in any order —
but both come before 3, which is the one that rewrites the render. From 5
onwards, text and export do not depend on each other.

They were built in this order, one at a time, with the suite green and the
stack redeployed at the end of each. Four of the ten had a defect that **only
verification on the real stack** found — the fade that painted black over the
lower layer, `ExportSpec` ignored by the cut-and-splice path, the routes
registered after the app's `mount`, and the music block presenting itself as a
match event. None of them showed up in the suite, and all of them showed up on
first use. Phase 9 also found, as a bonus, a service in a restart loop that no
test would see: they do not start containers.
